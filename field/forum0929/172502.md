Where does the bug appear (feature/product)? Grok Bot Describe the Bug After Grok Bot is closed, launching it again from the Start menu, a shortcut, or the executable can create background Electron processes but no visible application window. Restarting Windows temporarily recovers it. The failure was isolated to %APPDATA%\Grok Bot\window-state.json. The file contained a window rectangle far outside the only connected display, with width and height both equal to zero. On the failing launch, the Electron main process remained responsive but had MainWindowHandle = 0. Moving only window-state.json aside restored the visible window immediately. Bots, conversations, credentials, and Agent Computer data were not changed. Steps to Reproduce Run Grok Bot 0.57.1 on Windows with display scaling set to 150%. Use the app normally with its window maximized. Close the Grok Bot window using the title-bar close control. Launch Grok Bot again from Start, a shortcut, or %LOCALAPPDATA%\Programs\Grok Bot\Grok Bot.exe. Observe that the Electron process tree starts, but no Grok Bot window becomes visible. Additional launch attempts may create Crashpad reports and/or leave the process tree alive without a main window. This occurred repeatedly after closing the desktop app. A Windows restart allowed one normal opening, after which closing and reopening could trigger it again. Expected Behavior Grok Bot should validate persisted window geometry and either restore the last valid visible bounds or use default centered bounds. Closing and reopening the app should never require restarting Windows or manually resetting application state. Operating System Windows 10/11 Version Information Grok Bot: Version: 0.57.1 Release Track: stable Architecture: Windows x64 Electron: 42.1.0 OS: Windows Enterprise 25H2, build 26200.9448, x64 Display: one primary display, 1280x800 (working area 1280x752) Display scaling: 150% (AppliedDPI = 144) Additional Information Exact persisted state captured during the failure: { "version": 1, "normalBounds": { "x": -21326, "y": -21333, "width": 0, "height": 0 }, "isMaximized": true } At 150% scaling, those logical coordinates are approximately -31989, -32000 physical pixels, resembling Windows’ special minimized/off-screen coordinate. ## #11 Colin [STAFF] · 2026-09-21T18:52:30Z
Hey @francotgs , thanks for the detailed report. Two separate things are going on here. The window-state.json you captured is real and I’ve flagged it to the team: the app is recording the position of a minimized window as if it were the normal one. On its own, though, that file is ignored on the next launch (the app falls back to its default window size), so it is not what stops the window from appearing. The launches that produce no window are the ones in your log with exit_code=21 . That code means Windows refused to let the app start its sandboxed window process. Based on your report it sounds like the window is opening normally again! Have you reproduced the issue since it happened the first time?

## #12 francotgs · 2026-09-22T11:56:20Z
Hey Colin, thanks for looking into this. Yes, I reproduced it again and isolated a consistent launcher-context difference. A normal mouse click on the original icon launches the correct signed executable from the regular desktop Explorer process, with no arguments. The main process starts Crashpad and several utility processes, but the window process dies almost immediately, no window is created, and all Grok Bot processes exit. A failed manual launch also created a new approximately 34.8 MB Crashpad dump. This is not limited to reopening too quickly. Before the monitored test, Grok Bot had been closed for several minutes and process monitoring confirmed that no Grok Bot processes were running. The original icon still failed. I created a workaround that starts the exact same executable through a hidden, non-elevated PowerShell process. It also checks that no previous Grok Bot processes remain, but during the A/B comparison that condition was already satisfied immediately, so its success cannot be attributed to additional waiting. I manually tested repeated open/close cycles, including with the workaround pinned to the taskbar, and every launch succeeds. During the same Windows session, with no reboot or application-state change between tests, the original icon continues to fail. The reproducible A/B result is therefore: Explorer.exe -> Grok Bot.exe : fails Explorer.exe -> powershell.exe -> Grok Bot.exe : succeeds The window-state file was valid during these failures. This strongly suggests that the Windows launcher or inherited process/token context is relevant to the exit_code=21 sandbox failure. Could the team capture the underlying Win32 error for SBOX_ERROR_SET_THREAD_TOKEN , or compare the renderer launch token when the parent is Explorer versus PowerShell? I can provide the Crashpad dumps privately if useful.
