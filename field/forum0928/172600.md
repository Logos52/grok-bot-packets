## Post 10 @deanrie · 2026-09-23T07:47:23.890Z
Thanks for running the test all the way through. That’s exactly the part we needed to isolate.
Key fact: the silence reproduces on both AAC and ALAC, while ffmpeg and silencedetect show continuous audio, and the dropouts only show up in QuickTime on Mac. That means it’s not the audio codec. It’s how QuickTime interprets the file structure (edit lists, timing, A/V interleave) that you get from the still loop option -loop 1. This is a QuickTime plus ffmpeg behavior, not something on Cursor’s side.
First, a quick way to confirm the hypothesis: extract the same ALAC track into a plain .m4a file (no video) and play it in QuickTime. If the audio plays without dropouts, then the issue is specifically in the video track or the edit list. Also check the audio track offset:
ffprobe -v error -select_streams a -show_entries stream=start_time,time_base file.mov

Then I’d try changes one at a time:

Remove B-frames so you don’t get a CTS delay and an edit list on the video track: -bf 0 (or -x264-params bframes=0).
Set a reasonable video timescale and avoid negative timestamps: -video_track_timescale 24 -avoid_negative_ts make_zero.
Fix interleave: -max_interleave_delta 0.

Full command would look like this:
ffmpeg -loop 1 -framerate 24 -i cover.jpg -i track.wav -c:v libx264 -tune stillimage -bf 0 -pix_fmt yuv420p -r 24 -video_track_timescale 24 -c:a alac -max_interleave_delta 0 -avoid_negative_ts make_zero -shortest -movflags +faststart out.mov

A more reliable option is a two-step build. First render the still video without audio, then remux with audio using -c copy so the edit list from the loop doesn’t get carried into the final file.
Let me know what the .m4a test shows and whether -bf 0 helped. If the silence is still there, we can dig deeper into the container structure.

The documented behavior of -shortest + -loop 1 usually shows up as extra silence or an extended tail at the end of the file due to buffering and interleave behavior during muxing. An edit list in a MOV trims or shifts the start of a track. Neither of those, by itself, explains a drop happening in the middle of the track, so your correction correctly narrows the search.
A couple notes about the current file:

Framerate isn’t the suspect here anymore. In the confirmed-broken ALAC build you shared earlier, it uses -framerate 24 -r 24 and yuv420p, so the “1 fps + still + AAC” scenario is already ruled out for this specific file. It’s still worth double-checking the agent’s actual command just in case there’s a mismatch between what was intended and what was executed, but for the current .mov, low fps isn’t the cause.
If start trimming edit list and end tail from -shortest are off the table, a mid-track drop with continuous audio in ffprobe points most strongly to A/V interleave or packet ordering. QuickTime can lose the audio track when video packets are very sparse, and one long still image means very few video packets. That’s why -max_interleave_delta 0 and a two-step remux are still the main fix.

The deciding test is the .m4a audio-only file in QuickTime on Mac:

Plays cleanly means the issue is in the video track or container interleave, not the audio codec.
Still cuts out means we should dig into the audio stream itself.

Also try the .mov you already built with -bf 0. If it still has drops, the most reliable path is a two-step build where the final file is assembled from already clean video, so loop artifacts don’t carry over:

ffmpeg -i video_only.mov -i track.wav \
  -c:v copy -c:a alac -max_interleave_delta 0 \
  -movflags +faststart out.mov
